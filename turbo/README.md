# Generators

`@example/generators` scaffolds new packages, services and api-rspack subgraphs with
[`@turbo/gen`](https://turborepo.dev/docs/guides/generating-code) (Plop and Handlebars).

```sh
pnpm gen
```

```
What are you creating?
├─ package
│   └─ What kind?
│       ├─ library             frontend or backend; JIT or compiled (default: frontend → JIT, backend → compiled)
│       ├─ Nest module         compiled
│       └─ gRPC API (proto)    compiled; TypeScript generated by buf + ts-proto
├─ service                     Nest app bundled by rspack; modes: GraphQL / gRPC
│   ├─ always creates <name>-domain (a Nest module)
│   ├─ GraphQL → <name>-graphql-schema, registered with the gateway
│   └─ gRPC → <name>-proto
└─ api-rspack subgraph                a federated subgraph for one module of apps/api-rspack
    └─ which module?
```

## Scripted use

Each variant is also its own generator. `--args` answers its prompts in order, so tests, CI and agents can skip
the questions. Lists are comma-separated, and `""` is an empty list.

```sh
pnpm gen library     --args <name> <consumers> <frontend|backend> <jit|compiled>
pnpm gen nest-module --args <name> <consumers>
pnpm gen proto       --args <name> <consumers>                  # creates <name>-proto
pnpm gen service     --args <name> <github-team> <GraphQL,gRPC>
pnpm gen subgraph    --args <api-rspack-module>

pnpm gen library --args goals-client apps/web,apps/api-rspack backend compiled
pnpm gen service --args reviews example-org/platform GraphQL,gRPC
```

Consumers are workspace paths such as `apps/web`. `new` (plain `pnpm gen`) is interactive only: Plop can't answer
conditional prompts from `--args`.

## What a run changes

- Renders the new workspaces from `generators/templates/`.
- Adds a policy-bot rule to `.policy.yml`, owned by the service's team or by a placeholder to fill in.
- Services and subgraphs register in `packages/graphql-gateway-schema/main-supergraph.yaml`. Subgraphs also add
  a `SERVER_TYPE` case to `apps/api-rspack/src/main.ts` and a `dev:subgraph-<module>` script.
- Services and subgraphs add their processes to the `pnpm start` catalog (`packages/sears-catalog`), and the
  Procfile is regenerated after the install.
- Installs, as the last step: `pnpm -F <consumer> add <new-package>@workspace:* <its peers>` for each
  consumer, then one `pnpm install`, then builds proto packages so their generated code exists.
  `GENERATOR_SKIP_INSTALL=1` prints these commands instead of running them.

## Why `pnpm gen` and not `turbo gen`

`turbo gen` launches `npx @turbo/gen@<version>`. The root `devEngines` rejects npm, and npx would bypass the
lockfile anyway. So `@turbo/gen` is a pinned devDependency and `bin/gen.sh` runs it.

## Tests

```sh
pnpm -F @example/generators test             # every variant against a temporary fixture repo
CI=1 pnpm -F @example/generators test:generator  # generates, installs, checks, tests and builds a real service
```

The unit tests run each generator in its own fixture with its own copy of `generators/`, because `@turbo/gen`
writes a bundled config next to `config.ts` and parallel runs would race on it. A catalog test checks every
template dependency against the pnpm catalog.

## Layout

```
generators/
├─ config.ts           registers `new` and every variant
├─ new.ts              the interactive entry point
├─ variants/           library, nestModule, proto, service, subgraph
├─ shared/             answers, repo layout, file actions, policy, prompts, install
└─ templates/          Handlebars templates, one directory per variant
```
